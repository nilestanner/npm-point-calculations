## 2025-02-23 - Prevent Division by Zero resulting in NaN
**Vulnerability:** A missing check for zero distance in `findPointOnLine` resulted in a division by zero. This division by zero creates a `NaN` ratio, which propagates `NaN` into the X and Y coordinates. This `NaN` contamination can break data structures, invalidate rendering logic, or cause denial-of-service (DoS) if these invalid points trigger infinite loops or uncontrolled recursion in dependent systems.
**Learning:** Math functions that perform division using derived values (like Euclidean distance) are inherently risky when the inputs can result in a zero denominator. The logic incorrectly assumed start and end points would always be distinct.
**Prevention:** Always validate inputs or intermediate derived values before using them as denominators in mathematical operations. Return a safe, defined fallback (like the original starting point) when operations cannot be mathematically resolved safely.
## 2025-02-23 - Missing Input Validation in Structural Typing
**Vulnerability:** A lack of runtime input validation across mathematical functions allowed invalid inputs (like objects with string values, null, or objects containing NaN) to bypass structural typing assumptions in JavaScript, causing undefined behavior, propagation of NaN, or TypeErrors downstream. This is a DoS vector if it crashes the process or pollutes state with NaN.
**Learning:** TypeScript's structural typing does not protect the application at runtime. When exposing an API or processing input, mathematical operations are highly susceptible to NaN poisoning if the properties of structural types are not explicitly validated at the boundary.
**Prevention:** Implement runtime validation for all critical structural types and numeric inputs at the module boundary. Explicitly check for property existence, correct types (using `typeof`), and protect against `NaN` using `Number.isNaN()` before executing mathematical operations.
